# 1. P3 — Six-unit guided learning + free exploration

## 1.1 Core instructional mental model

**6개 주제(learning units)** = course-wide conceptual organization. **5단계** = existing cardiac-cycle mechanical stage walkthrough inside **unit 1**. **3수준** = original Guide difficulty/reading levels. **10문항** = original five-stage concept questions. These numbers never mix into one "11-step course" or duplicated progress counter.

UI copy:
- Global Learning header: "심장 전기생리학 학습 · 6개 주제"
- Below: "6개 주제는 학습 순서입니다. 기존 5단계 심장주기 탐색과 개념 10문항은 첫 번째 주제의 학습 도구로 그대로 제공해요."
- Keep progress reports separate: "**내가 완료 표시한 주제 2/6**" versus "**기존 개념 문항 제출 3/10**" (only display latter where meaningful). Do not call either competency/certification.

User goals: ① first-time student learns one idea at a time; ② intermediate student jumps directly to Wiggers/QTc; ③ student revisits a question/incorrect topic from Clinical P5 without losing the previous location.

## 1.2 Navigation and user-visible behavior (canonical)

**Top navigation**: ① Simulator | ② Learning | ③ Clinical (P4 remains disabled until P5).

**Within Learning**: second-level segmented buttons, labelled "[안내형 학습] [자유 탐색]". They **do not** create a new top-level route, RAF, animation mode, 3-tab navigation mechanism, or duplicate Guided State. Use native buttons with aria-pressed/controls consistent with router rather than partial role=tab.

### Guided course flow

1. First Learning open: no automatic Guide start, no simulation seek. Overview shows 6 short units + purpose and how to learn; initially selected unit 1 but not marked "viewed" or "complete".
2. Selecting a unit **updates reading** and focus heading; no auto-Scroll document to top if returning from Clinical, no native Timeline input and no Guide stage change.
3. Unit details show **one primary card per selected unit**, not all expanded at once. Desktop: stable compact chapter index alongside article; mobile: selected-unit selector/cards above article, naturally flowing vertical scroll.
4. Main reading order: **"이 단원에서 배울 것" (1 concrete goal) → "핵심 기전" (1–3 short paragraphs) → "왜 중요한가" (nursing relevance) → "직접 관찰하기" (clearly labelled explicit action) → optional "더 알아보기 / 근거"**.
5. "시뮬레이터에서 보기": route to Simulator; may select a designated original Electrical/Mechanical/Wiggers internal view **only because the student explicitly clicked this link**; maintains paused A/B and never starts playback/auto seek. If internal view change would alter original disclosure behavior, prefer route-only with instructions; verify before enabling automatic internal view switch.
6. "5단계 심장주기 학습 시작/이어보기" (Unit 1): invokes **existing Guide action**, not new quiz, with original Ready-first observation behavior only on the explicit click. Other course units never secretly call Guide stage selection.
7. Mark "학습 완료": **manual checkbox/button** after study, reversible, independent of reading and question submissions. An untouched unit isn't marked finished by rendering or by "free exploration".
8. "다음 단원": merely selects the next course unit. Never seeks. No locked unit and no forced completion.
9. Switch guided ↔ free: preserve chosen unit, marked completions, optional disclosure states, Guided answers/level/stage, and Clinical session. A free browse change can intentionally select a different unit without changing its completion.
10. Clinical P5 "관련 학습으로 이동": enter Learning on an explicit unit ID, keeping a **return destination** to the same clinical case/phase/question. Entering this unit does not start the five-stage Guide. "임상 문제로 돌아가기" (where context exists) navigates back without replacing any answers.

**Design decision (recommendation):** Course uses *self-marked completion* rather than auto-marking on scroll/answer/elapsed time. This is a study checklist, not a learning assessment. Future analytics can be separate, not invented for v1.13.

- Do **not** provide two competing "advanced" selectors that can drift.

## 1.4 Student-first layout contract

### Desktop ≥1024 CSS px

- Compact course index around **220–260px, flexibly** in available article width, with 6 single/two-line unit entries and distinct selected/marked states. Remaining text gets flexible 600–760px preferred reading region, but may shrink naturally; do not hardcode 900px chart beside it.
- Within article: readable heading, objective, 2–4 short paragraphs on core physiology, nursing anchor, one clear primary observation action, optional explanation/limits/references disclosures.
- Avoid putting a second realtime ECG Canvas into Learning. Existing Simulator link clearly indicates switching screens; no fake static ECG matching live A/B.
- Keep top-level 3-tab navigation perceptibly separate from within-Learning guided/free switches and 6-unit index.

### Tablet 768–1023 CSS px

- One main content column; condensed unit navigation above article or 2-column unit links when room permits. No cramped three-column index/article/side-summary.
- Avoid fixed-width diagrams or tables that push page sideways. All course card labels wrap without clipping.

### Mobile 320/360/390 CSS px

- One main scroll column; **active unit → objective → key concept → nursing meaning → action** within normal vertical flow.
- Small section navigator is scrollable/stackable but never leaves current unit invisible; no sideways swiping requirement to reach later units. Persistent six large expanded cards are discouraged.
- **Minimum implementation targets** (project usability goals, not all WCAG normative minima): main text ≥16 CSS px; secondary ≥14; line-height ~1.5–1.65; interaction targets **≥44×44 CSS px** for primary mobile controls; adequate separation; labels can wrap rather than truncate. WCAG 2.2 AA reference: regular text contrast ≥4.5:1 (large text ≥3:1), visual controls/icons needing identification ≥3:1; target size normative minimum 24×24 CSS px with exceptions; 200% text enlargement, 320px reflow (except meaningful charts), no loss of content.
- Do not make progress indicators solely colored. E.g., "[완료]" + count and visible selected indicator.
- No auto-playing illustrations, forced step carousel, fixed-height explanation container, unexplained English abbreviations, or automatic jumping on disclosure expansion.

### Reading guidance (project quality criteria)

- A primary card begins with **one bold core sentence**; only necessary 2–4 short paragraphs are visible. Long mechanisms/citations behind natural disclosure, but safety-critical caveats *also* appear near affected claims (e.g. relative units, cardiac-cycle non-simultaneity).
- Keep mobile core paragraph width within viewport, avoid shrinking fonts below planned baseline to fit. Expandable full original content is **never** deleted for brevity.
- Unanswered quiz explanation stays hidden until explicit original submission. Free-browse mode cannot silently reveal answers.
- Heading semantic order h2→h3→h4; focus-visible, labelled native buttons, status announcement only after user action, not every simulation frame.

## 1.5 P3 state, events and integration interface

**Minimal state (illustrative fields, not code implementation):**

**Event effects:**

- OPEN_GUIDE (explicit): delegates to original P2 Guide start, preserving pre-existing first-ready/native Timeline rules.
- OPEN_FROM_CLINICAL: selects unit + stores context; does not advance clinical phase, reveal answer, seek or reset.

**Technical APIs:** consume CardiacGuidedContent.stages, CardiacGuidedLearning read-only summary and CardiacLearning.getStageNarrative(stageId) only as-is; if additional content getters are needed, add a narrow *pure read-only* adapter and do not change original model. Unit metadata is immutable; content lookup handles unavailable source with visible "자료를 불러오지 못했습니다" fallback and diagnostic log, not silent blank or JS crash.

P3 deliverables: course-unit-data.js (new six-unit immutable mapping), course-view-v113.js (view/controller, no simulation state), small CSS and index wiring (load after P2 original Guide), tests/test_v113_patch3.py, in-app guide/patch notes/README/SPEC/DEVLOG.

# 2. P4 — Clinically coherent, static fictitious patient-case data

## 2.1 Explicit boundaries: P4 defines **data + validation**, not player UI

P4 may ship files, automated validators, manuscript and QA-only static preview, but **MUST NOT**:
- enable public Clinical button before P5 finishes;
- start questions/session/progress engine or create new patient clock;
- use the real simulator Sinus engine to render a pathological patient-specific ECG or physiological pressure/volume;
- invent clinically derived hemodynamic predictions or claim case data are the user's personal medical record;
- submit unreviewed case numbers/choice keys as validated medical learning materials.

Clinical case = a **single authored scenario with versioned observation snapshots**. Student actions in P5 change answers/revealed content, **not** patient observations. Reassessment is a predetermined, timestamped vignette.

## 2.2 First-case pedagogic specification

**Working name: "증상이 동반된 성인 서맥 — 숫자보다 관류와 상황을 먼저 확인"**.
Audience: nursing students. Intended judgment is **assessment, monitoring, prompt escalation/report and reevaluation**, rather than autonomous medication/pacing prescription.

AHA 2025 adult bradycardia algorithm uses heart rate **typically <50/min when bradyarrhythmic**, then investigates cardiopulmonary compromise signs such as hypotension, acutely altered mental status, shock, ischemic chest discomfort and acute heart failure; reversible causes must be considered. The original Simulator's **HR<60 "brady" category** remains a teaching-rate categorization, not identical to the AHA algorithm's clinical entry criterion. AHA also notes that bradycardia can be asymptomatic/physiologic. Sources in §2.8.

### Proposed learning outcomes (students should be able to…)

1. Recognize concerning low-rate **plus** symptoms/blood pressure and identify need for prompt assessment/escalation.
2. Interpret a provided **separate, clearly fictitious 12-lead ECG description/educational strip** as evidence to integrate with the patient, not a simulator-computed patient waveform.
3. Distinguish known, pending and unavailable laboratory/test findings, assess potential reversible contributors without assigning unsupported etiology.
4. Choose an appropriate **nursing-centered priority**: check patient/airway/breathing/circulation, monitor/verify pulse and ECG, promptly notify medical/rapid-response resources according to organizational protocol; never frame independent atropine/pacing decisions as nursing-student orders.
5. Reassess a later, independently authored observation and report whether safety concerns persist.

### Draft storyboard — **fictional illustration / NOT medically approved case data**

| Case time (Asia/Seoul local, +09:00) | Candidate patient/case information | Why the student sees it |
|---|---|---|
| 10:00 | Older adult, newly dizzy and weak. **Draft** HR 42/min and BP 86/54 mmHg; respiratory/mental/oxygenation data must be reviewed and completed before case release | Initial assessment prioritizes symptoms + circulation, not only HR |
| 10:05 | Separate 12-lead ECG **draft interpretation** of a regular slow rhythm with P–QRS relationship explicitly reviewed by a content expert; no live engine-derived strip | Distinguish ECG observation from actual bedside perfusion |
| 10:10 | Medication history & serum electrolytes/glucose information: **known result vs pending vs not obtained** states; numeric K+/glucose values and local lab reference ranges **TBD until clinical review** | Avoid inventing a diagnosis from absent labs; possible contributors can be checked |
| 10:15 | Fixed reassessment vitals and symptoms **TBD after full scenario consistency review**; no automatic improvement or deterioration based on selected answer | Students practice reassessment and timely further escalation |

The table is a **clinical-authoring storyboard, not validated patient observations**. It must not be imported verbatim as release data without clinical review. In P4 the exact age, history, medications, baseline/reassessment vitals, separate ECG interpretation, sample times, lab values/ranges, answer options/keys and rationales must be signed off **as one consistent fixture**.

Avoid alarmingly dramatic or unnecessarily dense patient history that overwhelms initial nursing priorities. No actual identifying health data. No fabricated sourced ECG image used as "real patient tracing".

## 2.3 Visible information architecture and staged disclosure

**Case list** (P5 presentation): one prominent card for first complete case; no blank case tabs/placeholders masquerading as usable cases. Title, 1-line goal, "가상 자료 / 교육용", start button.

**Case player future P5**:
1. Sticky *within case area only* minimal header: "가상 환자 · 사례 1 / 현재 단계", progress 1/4 etc. Never obscure primary site navigation or small mobile screens.
2. **Patient snapshot** always readable: chief complaint, time, HR, BP, symptoms, significant immediate red flags, source "가상 사례 자료".
3. **Vitals** in responsive pairs: value **with unit** and measuredAt, not random bright red badges alone; older/initial vs latest clearly labelled.
4. **ECG** separate education material in a readable card: recordedAt; static image/strip if legitimately authored/reviewed, alt/transcript, rhythm wording. "아래 ECG는 가상 사례에 제공된 별도 교육 자료이며 시뮬레이터 실시간 파형이 아닙니다."
5. **Labs** compact list/card: test name; result+unit or **pending/not available**; *that record's* reference interval if applicable; sample time; flag accompanied by textual meaning. Avoid five-column tiny mobile tables.
6. **Patient details / complete nursing report / full literature** in optional details, while **abnormal findings and clinically urgent information stay visible** outside optional disclosures.
7. A singular clear CTA per stage ("자료 확인" / "답안 제출" / "다음 단계") with visible back/return. Never hide diagnostic-critical observation behind a quiz answer.

**Display intent:** "**검사 미시행**" ≠ "**결과 대기 중**" ≠ "**정상**" ≠ numeric 0. Explicit clinical terminology is essential.

## 2.4 Static schema v1.0 — strict fields and validation semantics

One immutable authoring file clinical-cases.js (or checked JSON + read-only adapter), with schema in clinical-case-schema.js and a separate validator CLI/test. Keep clinical content, UI and session state separate.

**Case root:** schemaVersion:1, id (stable kebab-case), revision, language:'ko', audience:'nursing-students', reviewedStatus ('draft'|'clinical-reviewed'|'ready-for-p5'), title, learningObjectives[], caseSummary, patientContext (fictional flag, age group, sex where pertinent, chief complaint, symptom onset, relevant known history, medicationKnownStatus), phases[] ordering, observations{vitals,ecg,labs}, questions[], reassessments[], references[], learningLinks[], disclaimers.

**Each observation:** observationId unique, kind, **observedAt ISO 8601 with +09:00 offset** (if clock time given), **availableAt** distinct from collection/record time when delayed result, state ('known'|'pending'|'not-obtained'|'not-applicable'), provenance:'fictional-authored', sourceReferenceIds[], limitations[]. A result may not be displayed at a phase before availableAt; a pending result cannot carry a fake zero value. All dates/times must use a single scenario timeline.

- vitals: type, value, unit, patientCondition, measurementMethod where needed, observedAt.
- ecg: recordType ('static-educational-strip'|'expert-reviewed-text'), finding, rate and rhythm where justified, recordedAt, altOrTranscript, assetLicense/source, sourceReferenceIds, **explicitly not simulator-derived**. If ECG is only written interpretation, label "ECG 판독 요약(가상 사례)" rather than pretended actual trace.
- labs: testId, analyteName, result, unit, lower/upper or labReferenceRangeText, localLabContext, specimenCollectedAt, resultAvailableAt, resultState, interpretiveNote, referenceIds. For pending results **no numeric/normal interpretation**. Different lab methodologies/ranges mean use the fictional laboratory's own vetted reference interval, not an arbitrary globally universal one.
- chronology: baseline and later reassessment identified by distinct observation IDs, never overwrite old observation as though measured at the same time.

**Question object:** id stable, phase ('assessment'|'judgement'|'nursing-action'|'reassessment'), visibleContextIds[], prompt, choices[{id,text,feedback}], correctChoiceId, rationale, referenceIds[], linkedUnitIds[], levelOfJudgment:'nursing-assessment', consequenceText **not** claiming the patient's course changes with answer. Correct choice exists exactly once, wrong choices have **specific** educational feedback, not generic "틀렸음"; no correctness leaked pre-submit.

**References:** id, APA7 citation, source URL, sourceType, accessedOrReviewedAt, supportedClaimIds[], limits[]. The citation displayed next to a claim resolves to this source, not just a bibliography at page bottom. Avoid link rot via source title and access/review date.

**Release gate:** case.reviewedStatus = 'ready-for-p5' only with recorded review checklist and explicit verifier/date, **not** by passing JSON validation alone.

## 2.5 First case — proposed question allocation and answer criteria

Exactly **four core assessments** (one primary decision per phase) for v1.13 first case, minimizing cognitive burden and keeping review manageable. Do not add 10 duplicate physiology questions to Clinical; original ten stay in Learning.

| Phase | Proposed question (content draft, not final keyed choices) | Correctness criterion / explicit feedback |
|---|---|---|
| Patient assessment | "맥박이 느린 것 외에 지금 우선 함께 판단해야 할 자료는?" | Symptoms, BP, consciousness/perfusion, breathing; HR alone insufficient |
| Clinical judgement | "현재 환자 자료를 종합한 가장 적절한 위험도 판단은?" | Concerning hypotension and symptoms prompts immediate assessment and appropriate escalation; not simply benign because low rate alone |
| Nursing action | "간호학생·간호사의 우선 수행/보고 접근은?" | Bedside reassess ABC/perfusion, monitor pulse/ECG/BP, prompt team/rapid-response protocol, prepare/review orders; do not independently prescribe atropine, pacing, doses |
| Reassessment | "시간이 지난 후 새 활력징후와 증상을 보면 어떤 확인·보고가 필요한가?" | Compare observed symptoms/vitals, determine persistence/worsening and continued safety reporting without claiming one's answer produced physiologic outcome |

**Important:** actual three or four distractors and exact correctChoiceId, response feedback, rationale and citations are **P4 content drafting/review tasks**; these criteria are not a completed final question bank. Each wrong answer must explain *what is missing and why it matters*, not shame the learner. Avoid graded dose calculations/intervention prescriptions; clearly reference provider-directed ACLS interventions as outside the student's independent order role.

Correctness criteria need expert review under educational institutional scope and local escalation/standing-order policies, which vary.

## 2.6 Clinical authoring, review and QA pipeline

**Step 1 — clinical authoring, no live UI:** one versioned case manuscript maps chief complaint → time-stamped information → questions/options → correct keys/feedback → reassessment → references. Export/convert to static schema without separate handwritten UI versions.

**Step 2 — consistency validator (deterministic automation):**
- Unique case, observation, question, choice, reference, learning-unit IDs; valid enumerated status/phase.
- Every referenced ID resolves. Every graded question has 1 valid correct ID, ≥2 distinct choices, choice-specific feedback for **all** choices, rationale and ≥1 exact cited supporting source.
- Results: value/units/reference/timestamp obligatory for known quantitative labs; value prohibited for pending/not-obtained. Appropriate units match analyte; flag does not contradict its assigned local reference interval.
- observedAt ≤ availableAt for delays; start presentation cannot display future results; reassessment is later than baseline; baseline case events appear in coherent order.
- A fixed case timeline and case revision, no mutable patient state, no user-entered patient identity, no renderer side effects.
- P3 linkedUnitIds all match exactly one canonical six-unit id and can deep-link without auto Guiding/Seek.
- ECG record source is not script.js simulated patient ECG; image assets legally reusable or internally created for explicit hypothetical data and include accessible text.
- Mandatory patient-vitals context, units/symptoms; forbid "normal" conclusions based solely on reference interval and missing-context numeric claims.

**Step 3 — content/clinical verification (not replaceable by CI):**
- AHA bradycardia branch appropriateness reviewed in the exact hypothetical signs context; distinction between sinus simulator's <60 display category and ACLS commonly <50 bradyarrhythmia entry handled accurately.
- Patient baseline symptoms + HR/BP + ECG words + investigations + follow-up consistent. Identify whether ECG interpretation warrants an altered question, e.g., do **not** call a patient sinus bradycardic if the chosen expert-reviewed ECG instead shows AV dissociation.

### Distinctive P4 failure modes / mitigations

| Risk | Serious symptom in app | Response |
|---|---|---|
| Missing lab treated as value 0 or normal | Wrong clinical conclusion | Typed resultState and conditionally required value, validator forbids zero-default |
| Future lab exposed early | Student makes decision with unavailable info | availableAt / section visibility lookup, timeline-bound tests |
| ECG doesn't match narrative | Teaches incorrect rhythm | Clinical validation of original educational strip and text as one fixture |
| Clinical patient's HR becomes simulator HR | UI falsely displays patient waveform as computed | No binding to heartState, separate visible "가상 사례 자료" banner; test immutability |
| "HR<60" treated as AHA instability threshold | Incorrect clinical teaching | Explicit distinct educational/algorithm thresholds and symptoms evaluation |
| Normal lab taken to exclude disease | Unsafe inference | Range interpreted in clinical context; pending/not taken visually distinct |
| Too many simultaneous dense tables | Mobile scrolling fatigue / illegible results | Vitals pair cards; mobile lab per-result cards with readable labels/time/range; full details optional |
| Answer key / feedback contradict cited evidence | Wrong learning with high confidence | Per-choice source refs + human clinical review + cross-field semantic audit |
| Untested fields result in blank Clinical tab | Student cannot understand case | Case release forbidden before P5; validator catches missing state/renderer labels |
| Quiz results accidentally cleared by tab switch | Learner loses submitted judgments | P4 owns **no** session, P5 state isolation and route roundtrip contract |

## 2.7 Accessibility/performance/readability gates shared by P3 and P4

- Viewports: **320, 360, 390, 768, 900, 1024, 1366** CSS px plus actual user mobile & PC.
- Text at 200% resize, WCAG 2.2 minimum AA contrast targets; keyboard traversal, Escape/back/focus restore, visually prominent focus, answer labels described without color alone.
- Mobile **project goals**: 16px primary text, 14px ancillary minimum, 44px primary touch areas, ≥1.5 line height; keep chart exception scroll local, not entire document.
- No auto-restored scroll that jumps the learner away from the selected unit, no hidden screen focus, no infinite rerenders or multiple resize/RAF handlers.
- Long Korean medical terms and English abbreviations must wrap; first use expansion e.g. "좌심실(LV)" and "방실 전도(PR)" where appropriate.
- Clinical safety-critical information always visible; details may hide additional explanation and citations, **never** essential danger signs before decision.
- QA logs must distinguish "Chrome/Playwright screenshot passed" from **independent human UX/clinical review**.

# 3. Coordinated implementation handoff for P2–P6 (user's single future development effort)

**Plan now / implement later.** Avoid prematurely enabling Clinical or changing simulation engine.

Implementation branch: one new integration branch created from freshly verified stable main at the time of execution. **Not** a giant file replacement: checkpointed commits/test evidence in dependency order and one final reviewed integration PR (or separated review PRs if CI/change scope requires). Main remains functional until the complete product passes gates.

1. **P2 checkpoint:** one original Guided panel moved behind the real Learning host; preserve selected stage/difficulty/ten submitted answers, original seek semantics and live Inspector. Run old/new regression and screenshot gates.
2. **P3 checkpoint:** six-unit metadata/reading/navigation/free browse; no new quiz bank or clocks. Run content-source parity, 6-unit navigation, UI/mobile/scale/ARIA, clinical deep-link placeholder validation.
3. **P4 checkpoint:** one reviewed immutable clinical fixture, strict schema and source validator, QA-only data sheet. Clinical public button still disabled. Run negative tests (missing lab, wrong units, mismatched IDs, future lab, ECG contradiction needing manual review) and source signoff.
4. **P5 checkpoint:** independent case session, questions, nursing priority/reassessment, full result comparison, Learning→same Clinical return and explicit reset. Enable public Clinical only after all first-case screens have complete validated content.
5. **P6 checkpoint:** all original tests + P2–P5, performance, no overflow, accessibility, internal UI review, docs and full CI. Merge and confirm main CI; final label still withheld until actual user PC/mobile and clinical-material approval.

**Proposed go/no-go dashboard:**
- Simulation time invariants: 0 unintended Timeline inputs/clock jumps across unit browsing and case reading; original explicit Guide seek continues to work.

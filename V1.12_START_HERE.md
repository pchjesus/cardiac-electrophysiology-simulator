## 2. What v1.12 should accomplish

**Recommended working title:** Guided Cardiac Cycle Learning / 심장 주기 단계별 학습.

Make a clinically careful *learning layer*, not another dense dashboard:
- Optional guided, step-by-step prompts for five phases: ventricular filling, atrial systole, isovolumetric contraction, ventricular ejection, isovolumetric relaxation.
- Explicitly align each prompt with ECG activation, the existing relative LA/LV/aortic pressure / volume visual, valve events/S1-S2 and qualitative nursing assessment.
- Beginner vs advanced detail can reuse already reviewed v1.10 nursing/physiology source data; keep existing normal interactive simulation as default.
- Questions should check qualitative concepts (which valve is open? why does pressure increase with constant volume? why can P wave precede atrial contraction?), rather than medical prediction or numerical output.
- Never mistake the existing HR classification presets (72, 50, 120 bpm) for specific patient diagnoses or clinical instability. If case examples are proposed, explicitly mark them as **hypothetical**, source their assumptions and seek an explicit UX/educational scope decision before implementing.

**Proposed non-goals for v1.12 initial patch:** arrhythmia electrophysiological remodeling, AV block, heart failure, ischemia, invasive pressure simulation, cardiac output/EF computation or patient-care decision support. Those need a distinct, medically reviewed modeling plan and must not be silently added through interface changes.

## 3. Source-first clinical review

Ground existing and new descriptions in reliable cardiac physiology, separating:
- established cardiac cycle / pressure-gradient–valve relations;
- educational conventions and normalized curves;
- qualitative nursing observations or assessment (not clinical actions prescribed by the simulator);
- known model limits, especially high-HR QT/QTc, half-open Wiggers event boundaries and legacy Mechanical rounding.

Existing reference sources are in README.md / SPEC.md (OpenStax, StatPearls, AHA), and do **not** validate this simulator's numerical approximation. For new content, verify primary or clinically authoritative sources and add APA 7th citations.

## 4. Development and risk protocol

1. After the user reviews v1.11.1 on their PC/mobile, record genuine UI issues before growing the application.
2. Define which visual/educational choice requires user decision (guided overlay vs optional tab vs separate walk-through), then explain trade-offs; do not change the accepted compact default without approval.
3. Implement a small initial guided-learning patch on a separate branch. Reuse existing timing and descriptive data, with no independent animation or model-state source.
4. Distinguish **learning progress** from the running simulation's A/B state. Guided steps may seek via existing Timeline only through explicit user interaction, not covertly.
5. Preserve all 10 automated test stages (v1.8–v1.11.1) and add new v1.12-specific browser / semantic tests; check keyboard and mobile 360/390/768/1366 widths, history/guide popups, Wiggers local scroll, detailed nursing text, Reset and frame timing.
6. Compare actual browser captures for compact and expanded modes. A passing headless test is not physical-device visual sign-off.
7. Document design, risks, validation, release steps, and update categorized patch history/user guide in the app. Only merge after branch and final main CI success.

## 5. Risks in descending priority

- **Clinical misinterpretation:** Do not teach normalized ventricular volume as EF or actual stroke volume; do not equate ECG wave boundaries exactly with valve events.
- **State collision:** Guided learning must not reset/pause original simulation without learner action.
- **Vertical regrowth:** Guided content must be opt-in so default compact layout remains useful at 1366×768.
- **Accessibility:** No keyboard trap or invisible text in collapsed disclosures; native details must remain independently operable.
- **Accumulated CSS/JS fragility:** Avoid expanding selectors across unrelated panels or rewiring pre-existing event handlers. If complexity warrants refactoring, require separate regression-bearing patch.
